# 性能测试方法

针对目标消息传输方式，测量从 HTTP 准入到订单结算完成的完整链路。会话准备和结算轮询不计入 HTTP 准入延迟，但应单独报告结算完成情况。

每次测试记录以下信息：

- CPU 型号和核心数、操作系统/容器运行时、编译器、构建类型及依赖镜像版本；
- 网关工作线程、消费者工作线程、MySQL 连接池大小，以及 Redis、RabbitMQ、MySQL 配置；
- 请求数、客户端并发数、库存/配额，以及限速提交时使用的请求速率；
- HTTP 状态码统计、成功准入吞吐 RPS、P50/P95/P99、服务端错误和传输错误；
- 最终请求状态、命令积压、消费者/死信队列计数及库存不变量。

建议测试并发数 100、300、600 和 1000，并增加一次限速稳定负载测试。单个测试点不代表容量承诺。调整工作线程数、锁或队列预取值前，应先对可复现的瓶颈进行性能分析。

运行 `deploy/scripts/benchmark_rabbitmq.sh`；默认将报告写入 `benchmarks/results/rabbitmq-single-node.json`。本地内存测试结果不代表 RabbitMQ 全链路性能，二者不可直接比较。

## 已记录样本

2026-10-10，在当前工作树的 macOS arm64 隔离 Docker Compose 环境中，客户端并发数为 300 时接收了 1,000/1,000 个请求。准入吞吐为 245.29 RPS，p50/p95/p99 延迟为 1050.245/1109.768/1127.305 毫秒。全部已接收请求均完成结算并进入 `PENDING_PAYMENT`，队列积压归零；初始库存为 1,000，Redis 最终库存为 `available=0,reserved=1000,sold=0`。准备阶段耗时 252.397 秒，未计入准入耗时。环境及原始数据见 [`../benchmarks/results/rabbitmq-single-node.json`](../benchmarks/results/rabbitmq-single-node.json)。这是一次本地单机测试，不能据此推断生产容量。API 的 `/debug/stats` 消费者计数器只统计当前进程，因此报告不会将其作为全局计数，也不会宣称测得了死信队列数量。
